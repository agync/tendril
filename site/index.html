Pair two devices. No account, no server to trust.

A phone that syncs with a laptop. A desktop app you reach from your phone. Every app like this rebuilds pairing, keys, permissions and revocation.

Tendril is those parts, built once in a Rust core. You show a code, a person compares a check string, and the two devices talk directly.

Using an app built on Tendril? What it means for you

Six things every device-to-device app rebuilds.

A socket is the easy part. Apps most often get 02 and 04 wrong.

  1. 01

    Finding each other

    Six ways to connect, from a local socket to a relay. Every path is untrusted. It counts only once the peer proves who it is.

  2. 02

    Knowing it is the right device

    The code is bound to this one handshake. Then a person compares a 16-character check string on both screens. Machines with no screen enroll with a signed, single-use token instead.

  3. 03

    Where keys live

    Files only your user account can read on desktops and servers, wiped from memory after use. Keychain and Android Keystore adapters for mobile.

  4. 04

    Revoking a lost device

    Each device is pending, active or revoked. Signed revocation lists also reach sessions that are already open.

  5. 05

    What the link may do

    Nothing, until a signed grant (a permission) says so. Grants expire. They can be passed on, but only narrower, and at most four times.

  6. 06

    When the network changes

    The pairing belongs to the devices, not the path. The host signs every route it can be reached on and sends a new list when they change. A new path needs a new handshake, never a new pairing.

How each one works

One scan finds the host at home and away.

A host's QR code carries every route it can be reached on, such as its home network address, its address on a VPN like a tailnet, and a relay, all signed by the host. Later connects try them nearest first, with nothing to type or approve.

Built on other projects, not in place of them.

Tendril does not replace iroh, Noise or the platform keystores. It uses them, and adds the layer every app ends up writing itself, everything between your app and the network.

Serve, pair, confirm, grant.

The same steps in every language. Your app owns the screens and the names of its grants. Tendril owns everything with a key in it.

$ uv add tendril-sdk
import json, tendril

host = tendril.Endpoint("./laptop-state", "laptop")
addr = host.serve_direct("127.0.0.1:0")
code = host.issue_code("lan")                     # show as text or a QR

req = json.loads(host.pair_accept(5000))
host.confirm_peer(req["device_id"], req["sas"])   # after a person compares the check string
grant = host.mint_grant(req["device_id"], ["notes.sync"], ttl_secs=3600)

session = host.accept_session(5000)
session.authorize("notes.sync")                   # True

What we borrow, and what we own.

The algorithms are standard and used unchanged. The new parts are named, so review effort can go there. There has been no third-party audit yet.

Borrowed, proven elsewhere

Key exchange
X25519 and ML-KEM-768 (NIST FIPS 203)
Signatures
Ed25519 and ML-DSA-65 (NIST FIPS 204), used together. Both must verify
Signed bytes
Canonical JSON (RFC 8785)
Code proof
Argon2id: 64 MiB and 3 passes, or 19 MiB and 2 passes in Wire v2 pairing
Peer-to-peer path
QUIC and hole punching, via iroh

New, and ours

Hybrid handshake
Noise_XXhfs_25519+MLKEM768_ChaChaPoly_SHA256, in our own Noise code. Checked against a separate Go version
Code proof
Works only on the connection it was made for
Signed routes
The host signs the addresses in its QR code and every later update. A route only says where to dial. The handshake still has to prove the host
Confirm, then grant
Approving a device and granting it anything are separate steps
Grants
Default deny. Exact names or a prefix, no patterns
Revocation
Signed lists that only move forward, pushed into live sessions
Wire v2
An opt-in privacy mode: hourly mailbox keys, padded sizes, and a decoy reply for strangers who probe a host

A relay cannot see

  • Your data
  • Which grants exist
  • Device names
  • The pairing code

A relay can see

  • IP addresses
  • When devices connect, and how much they send
  • The key a waiting device uses as its mailbox. By default it never changes, so a relay can link that device's sessions

Wire v2, an opt-in mode, changes the mailbox key every hour, rounds sizes up to fixed steps and varies the timing of keepalives. Addresses, and when devices send, stay visible. What it hides
