# Conformance Vectors

Canonical byte-for-byte test vectors for identity fingerprints, pairing MACs,
signed key rotations, RFC 8785 JCS capability grants, revocation lists, signed
pairing route statements and route sets, and Noise_XXhfs (hybrid X25519 +
ML-KEM-768) handshake transcripts.

## Files

- `fingerprints.json`: `device_id`, `host_fingerprint`, `device_fingerprint`, and `pairing_sas`
- `pairing_mac.json`: 3-group and 2-group normalized codes, `argon2id` keys, `code_mac`, and the human signing key claim (`key_proof`)
- `rotation.json`: hybrid-signed `RotationRecord` links (`seq = 1`, `seq = 2`, 4031-byte signed payloads) and fork rejection vector
- `grants.json`: JCS canonical grant signing (hybrid Ed25519 + ML-DSA-65), valid delegation, invalid widened delegation, and `RevocationList`
- `handshake.json`: full deterministic `pair` and `session` `Noise_XXhfs_25519+MLKEM768_ChaChaPoly_SHA256` transcripts including `0x04 REKEY`, and `session_refusal_v1`: a session with a revoked initiator, driven through the real responder, ending in the 21-byte encrypted `0x07 CLOSE 4001` (`close_inner_hex`, `close_frame_hex`). Its ephemeral seeds are the expanded `x25519`, ML-KEM keygen (`d || z`) and encapsulation (`m`) seeds, and `responder_signing_seed_hex` / `responder_signing_mldsa_seed_hex` rebuild the `HostHello` key
- `m2m_enrollment.json`: signed M2M `pair.enroll` token, 3373-byte hybrid `enroll_proof`, `PairClaim`, replay rejection, and enrollment reply `route_set` (host-signed and other-signer) vectors
- `wire_v2.json`: Wire v2 preambles, blinded `/v2/relay` hourly epoch tokens, blinded `iroh://v2` hourly Ed25519 epoch identities and boundary overlap windows (`blinded_p2p`), Tier 2 HMAC & Tier 3 Ed25519 JCS `RelayTicket` admission, pseudonymous v2 reconnect (`0x09 PADDED` / `0x08 PADDING`), hybrid `Argon2id` PAKE + `ML-KEM-768` pairing vectors, and `v2_refusal`: the sealed refusal envelope (`spec/wire-v2.md` Section 3.1.5) for codes `4001` and `4004` from fixed `reconnect_secret`, `rendezvous_nonce`, `h_pre` and `bucket`, with `refusal_seal_key_hex`, each `refusal_pt_hex` and `sealed_refusal_hex`, and `negatives` an initiator rejects (`open_with` names the key; `expected_error` is `host_key_unverified` for a cross-key open and `protocol_violation` for a bad version, non-zero padding or code `4002`)
- `groups.json`: deterministic `group_id`, hybrid-signed `GroupManifest` chain (root-signed and co-admin-signed with `admin_grant`), rejection cases, `pair_bootstrap` / `group_mailbox` HKDF outputs, the `0x0B` frame, and `SessionHello.groups`
- `routes.json`: the `0x0C ROUTE_SET` codec (`spec/wire-v1.md` Section 5.2) under the top-level key `route_set`, plus `session_hello_route_seq`. `route_set` holds the fixed host key material (`static_scalar_hex`, `static_pub_hex`, `signing_seed_hex`, `signing_mldsa_seed_hex`, `signing_pub_hex`, `sh_hex`) and `domain_hex` (`"tendril-route-set-v1\0"`); `sign_deterministic`, a list of deterministically signed sets (including `iroh_v2` carrying `iroh://v2?relay=https://relay.example.com`), each with `name`, `seq`, `issued_at`, `routes`, `body_hex`, `signed_bytes_hex` (the domain plus the body) and `sig_hex` (the 3,373-byte hybrid signature), where the wire payload is reconstructed as `body_hex` followed by `sig_hex`; and `decode_rejections`, a list of structurally invalid payloads (`name`, `body_hex`, `zero_filler_len`, including `iroh_v2_addr`) that decoders must reject. `session_hello_route_seq` gives the `SessionHello` JSON (`json`) carrying `route_seq` (`route_seq`). The pairing URI route statement (`spec/pairing-v1.md` Section 6.5: the exact `rs_input` bytes and the Ed25519 `rs` signature for a fixed URI) is carried under the top-level key `pairing_route_statement` (`uri`, `uri_bytes_before_rs`, `hints`, `route_seq`, `domain_hex`, `rs_input_hex`, `ed25519_pub_hex`, `rs_hex`). The pre-`msg3` checks of a URI-bound initiator (`spec/pairing-v1.md` Section 6.5 steps 1-3) are under `pairing_route_check`. `uri_identity` holds the seeds of the key the rotated cases' URIs were issued for and `rotated_at`, the time it rotated into the fixed `route_set` key. Each case in `cases` (`verified`, `unsigned`, `route_key_rotated`, `route_key_rotated_stale_rs`, `invalid_rs`, `rp_mismatch`, `rp_mismatch_and_invalid_rs`, `operator_key_mismatch`, `unchained_key`) gives the `uri`; the `responder` (`uri_key`, `rotated_from_uri_key` with a one-record rotation chain, or `unrelated_key` with no chain); the key it presents (`presented_static_pub_hex`, `presented_ed25519_pub_hex`, `presented_signing_pub_sha256_hex`, `presented_rotation_seq`), always the fixed `route_set` key; an optional operator `URL#key` (`operator_relay_key_hex`); the expected `pin_ok`, `relay_pub_ok` and `route_check` (both `null` when the pin fails); the refusal (`commit_error`: `host_key_unverified`, `invalid_pairing_uri` or `null` when `msg3` is written); and the wires it holds on (`wires`). Rust replays every case through a real Wire v1 and v2 PAKE handshake, deferred and not. Go recomputes `relay_pub_ok`, `route_check` and `commit_error` from the bytes and checks the pin only for `uri_key`; it does not verify rotation chains and takes `pin_ok` for the other responders from the Rust replay.
- `verify_go/`: independent Go test suite reproducing every vector byte-for-byte (`crypto/mlkem` + `circl/mldsa65`)

## Commands

```bash
cargo run -p tendril-core --example gen_vectors   # regenerate canonical vectors
cargo run -p tendril-core --example gen_group_vectors   # regenerate groups.json
cargo run -p tendril-core --example gen_route_vectors   # regenerate routes.json
make vectors/check                                # verify Rust and Go suites
```
